# Intelligent stickers

- Module: incoming image understanding, group-scoped semantic storage, QQ-native custom faces, and low-frequency reactions.
- Code: `yebot/runtime/stickers/`, `yebot/runtime/tools/catalog.py`, `yebot/runtime/tools/onebot.py`, `main.py`
- Milestone: [M7](../roadmap.md#m7)
- Status: in progress
- Updated: 2026-08-02

## Responsibilities and boundaries

The module handles image components only. It does not retain the full source
message. AstrBot supplies image paths and, when needed, a short caption to the
restricted background agent, which decides whether an image is useful. YeBot stores the image and bounded meaning
metadata, keeps groups isolated, and sends only a sticker ID from the current
group through OneBot.

Automatic collection is enabled by default. Automatic reactions are also enabled,
but use a separate low-frequency policy with probability, optional cooldown, quiet
hours, and a daily group limit. The default cooldown is disabled. A successful
OneBot send consumes one allowance.

## Data flow

```text
group image event
  -> image-caption provider when the active model may lose images
  -> restricted agent [sticker.consider only]
  -> StickerService -> StickerStore(index.json + files/<sha256>)
  -> NapCat add_custom_face (native QQ library)

group message
  -> sticker send policy (no mention required)
  -> restricted agent [sticker.search + sticker.send]
  -> OneBot send_group_msg(mface segment, or image fallback)
```

The `data/yebot_stickers` directory is shared by AstrBot and NapCat. Images are
content-addressed with SHA-256, and metadata is written with an atomic JSON
replacement. Duplicate image content does not create a second file.

## Key decisions

- The collection path keeps the original image paths for the tool, and asks
  AstrBot's configured image-caption provider for a short text hint first. This
  keeps collection reliable when the chat provider falls back to a text-only
  model, which would otherwise receive only `[Image]`.
- The collection agent can run without an @ mention, but it has only
  `yebot_sticker_consider` and cannot send messages.
- The reaction agent can run without an @ mention, but it has only
  `yebot_sticker_search` and `yebot_sticker_send`; it sends at most one image.
- Automatic reaction jobs use a serialized send queue, so cooldown and daily
  limits are checked immediately before each agent run.
- `observe_only=true` pauses both automatic paths. `tool_dry_run=true` prevents
  real sends and does not consume the reaction quota.
- `sticker.search` and `sticker.send` are group-scoped. A sticker ID from another
  group is rejected by the store boundary. A semantic search with no exact
  matches falls back to the newest stickers in the current group and marks the
  response with `fallback=true`, so natural requests such as "发个表情包"
  still have candidates to choose from.
- Local metadata remains the source of semantic meaning, tags, usage counts, and
  group isolation. Native QQ identifiers are persisted alongside it, because QQ's
  custom-face library is account-wide rather than group-scoped.
- NapCat's `add_custom_face` and `fetch_custom_face_detail` are called through
  AstrBot's raw `bot.api.call_action`. Standard `emojiId/key` fields are sent as
  a native `mface`; the current personal-emoji detail shape (`resId/url/md5`)
  is persisted and sent as an image URL. Local image sending remains the final
  fallback.
- Existing local records are migrated once after the first non-dry-run group
  event. An item that still lacks a native record can be retried when it is
  explicitly sent or collected, without re-migrating the entire library on
  every message.
- Sticker files and the JSON index are written with read permissions for the
  shared NapCat uid, avoiding the `0600 root:root` files created by `mkstemp`.

## Current implementation

`StickerStore` provides content de-duplication, restart-safe JSON persistence,
group search, usage counts, and native identifier persistence. `native.py`
normalizes the different camelCase/snake_case response shapes used by NapCat.
`StickerService` reads AstrBot image components from a local path or base64 data
URL, performs best-effort native collection/migration, and keeps image fallback.
`native.py` accepts both standard mface identifiers and NapCat personal-face
resource records. `main.py` creates two restricted background agents, supplies
caption hints for image collection, tracks their tasks for clean termination,
and logs whether a collection or send decision actually happened.

## Verification

`tests/test_stickers.py` covers de-duplication, restart recovery, declined
collection, semantic search, native identifier persistence, both NapCat response
shapes, `mface` construction, QQ URL sending, and image fallback.
`tests/test_policy.py` covers independent no-mention low-frequency gates, cooldown,
daily limits, quiet hours, and probability. The release gate is pytest, Ruff, and
strict mypy. Container acceptance should send an image, confirm an automatic
collection decision in logs or `index.json`, then send several normal messages and
check that an occasional saved image arrives without an explicit tool name.
