# Intelligent stickers

- Module: incoming image understanding, shared semantic storage, QQ-native custom faces, and low-frequency reactions.
- Code: `yebot/runtime/stickers/`, `yebot/runtime/tools/catalog.py`, `yebot/runtime/tools/onebot.py`, `main.py`
- Milestone: [M7](../roadmap.md#m7)
- Status: in progress
- Updated: 2026-08-13

## Responsibilities and boundaries

The module handles image components only. It does not retain the full source
message. AstrBot supplies image paths and, when needed, a short caption to the
restricted background agent, which decides whether an image is useful. YeBot stores the image and bounded meaning
metadata, keeps the source group for traceability, and sends only a sticker ID
from the shared library through OneBot.

Automatic collection is enabled by default, with precision favored over recall.
Only an already-made meme, reaction sticker, or cartoon reaction is eligible.
Ordinary photos, including expressive pet or portrait images, screenshots,
documents, food, scenery, and product images are rejected. Automatic reactions
start only after the main Agent has produced a group reply. The restricted agent
then judges whether a sticker adds value, searches the shared library once, and
sends at most one strong match. There is no automatic sticker probability,
cooldown, quiet-hours window, or daily sticker limit.

## Data flow

```text
group image event
  -> factual image-caption provider when the active model may lose images
  -> restricted classifier [kind + standalone reaction + confidence]
  -> restricted agent [sticker.consider only]
  -> StickerService -> StickerStore(index.json + files/<sha256>)
  -> NapCat add_custom_face (native QQ library)

main Agent group reply
  -> restricted reaction agent [context judgement]
  -> one sticker.search
  -> optional one sticker.send
  -> OneBot send_group_msg(mface segment, or image fallback)
```

The `data/yebot_stickers` directory is shared by AstrBot and NapCat. Images are
content-addressed with SHA-256, and metadata is written with an atomic JSON
replacement. Duplicate image content does not create a second file.

## Key decisions

- The collection path keeps the original image paths for the tool, and asks
  AstrBot's configured image-caption provider for an objective visual description
  first. It deliberately does not state an emotional-usefulness conclusion, so a
  caption cannot bias the later collection decision. This keeps collection
  reliable when the chat provider falls back to a text-only model, which would
  otherwise receive only `[Image]`.
- When the active provider declares image input support, the collection path
  skips the extra caption request. Text-only fallback providers use
  `StickerCaptionCache`, keyed by image content fingerprint, provider, model,
  and prompt version; successful descriptions stay in memory for 24 hours.
- Collection calls must provide one visual kind, `reaction_ready`, and a numeric
  confidence. `StickerService` enforces all three after the model call: only
  `meme`, `reaction_sticker`, and `cartoon_reaction` can be saved; the default
  confidence floor is `0.90`. A model cannot bypass this by merely setting
  `should_collect=true`.
- The AstrBot local function-tool adapter supplies conservative defaults when a
  model call omits a decision field: `should_collect=false`, `asset_kind=other`,
  `reaction_ready=false`, and `confidence=0`. This keeps malformed calls from
  raising inside AstrBot, while the YeBot gateway remains the final validator.
- The collection agent can run without an @ mention, but it has only
  `yebot_sticker_consider` and cannot send messages. The allowance is carried
  on the event as well as a context variable because AstrBot may execute tool
  callbacks in a separate task context.
- The reaction agent can run without an @ mention, but it has only
  `yebot_sticker_search` and `yebot_sticker_send`; it sends at most one image.
- Automatic reaction jobs start only after a non-empty main-agent response tied
  to a current human group message. The observer registers a per-event token in
  addition to the `group_id:message_id` source key; the send gate rejects
  missing or mismatched keys, bot-authored messages, background tasks, and
  scheduled tasks. Each token can be consumed once, only one automatic sticker
  agent can run at a time, and one run makes at most one search and one send
  attempt. A failed send is not retried, so slow or reused events cannot form a
  delayed sticker backlog while the group is quiet.
- `observe_only=true` pauses both automatic paths. `tool_dry_run=true` prevents
  real sends; it does not change the one-search or one-send decision boundary.
- `sticker.search` and `sticker.send` use one shared library across all groups.
  `group_id` remains stored as the source group for traceability, but it is not
  an access boundary. New duplicate image content is de-duplicated globally;
  older group-prefixed sticker IDs remain readable. A semantic search with no
  exact matches falls back to the newest global stickers and marks the response
  with `fallback=true`, so natural requests such as "发个表情包" still have
  candidates to choose from.
- Local metadata remains the source of semantic meaning, tags, usage counts, and
  source tracking. Native QQ identifiers are persisted alongside it, because
  QQ's custom-face library is account-wide.
- NapCat's `add_custom_face` and `fetch_custom_face_detail` are called through
  AstrBot's raw `bot.api.call_action`. Standard `emojiId/key` fields are sent as
  a native `mface`; the current personal-emoji detail shape (`resId/url/md5`)
  is persisted and sent as an image URL. Local image sending remains the final
  fallback.
- Existing local records are migrated once after the first non-dry-run group
  event. An item that still lacks a native record can be retried when it is
  explicitly sent or collected, without re-migrating the entire library on
  every message.
- Sticker files and the JSON index are written with read permissions for the
  shared NapCat uid, avoiding the `0600 root:root` files created by `mkstemp`.
- `sticker.list` and `sticker.delete` are owner-only global tools for reviewing
  and removing entries from YeBot's shared local library. They do not claim to
  delete the corresponding QQ client-side personal custom-face record, because
  that requires a verified NapCat deletion API.
- When YeBot sends a saved sticker, the local record keeps a bounded set of the
  resulting QQ message IDs. An owner can reply to one of those bot messages and
  request deletion without knowing the internal `sticker_id`. The handler verifies
  the quoted message belongs to the current group and was sent by the bot. Older
  messages can fall back to unique native `mface` or saved native-image URL matching.
- An explicit request such as "收藏上面那几个表情包" loads a bounded set of
  recent images from the current group through `get_group_msg_history` and,
  when needed, `get_image`. The images are attached to the current event only
  for the restricted classifier; they are never treated as ordinary chat
  history and the current group remains the read scope.
- When the user replies to an image and asks to save or collect it, the same
  collection tool first reads that reply through `get_msg`. It prefers the
  OneBot file identifier and `get_image` result over a remote image URL, then
  attaches exactly that image to the restricted classifier. A failed explicit
  reply lookup does not fall through to an unrelated recent image; history is
  used only when the current request has no reply target.

## Current implementation

`StickerStore` provides content de-duplication, restart-safe JSON persistence,
global search, usage counts, visual-kind/confidence metadata, owner deletion,
bounded outbound message-ID tracking, and native identifier persistence. Legacy
records decode as `legacy` so older indexes remain readable. `native.py` normalizes the different camelCase/snake_case
response shapes used by NapCat. `StickerService` reads AstrBot image components
from a local path or base64 data URL, applies the strict quality gate before
writing, performs best-effort native collection/migration, and keeps image fallback.
`native.py` accepts both standard mface identifiers and NapCat personal-face
resource records. `main.py` creates two restricted background agents, supplies
caption hints for image collection, tracks their tasks for clean termination,
defaults incomplete collection-tool calls to a no-collect decision, and logs
whether a collection or send decision actually happened. `history.py`
extracts structured and legacy CQ image segments from bounded OneBot history.
`StickerImageRef` preserves the original message and sender IDs when a
historical image is saved, while the temporary event attachment lets the same
classifier and quality gate handle current and historical images.
`reply.py` reuses the reply-image resolver for explicit save/collect requests,
preserving the source message and sender IDs.
`main.py` shares the caption cache across events, so automatic collection and
explicit historical collection can reuse the same successful image description.

## Verification

`tests/test_stickers.py` covers de-duplication, restart recovery, declined
collection, rejection of a high-confidence ordinary photo, confidence rejection,
owner-only review/deletion, reply-based deletion, semantic search, native identifier
persistence, both NapCat response shapes, `mface` construction, QQ URL sending,
and image fallback.
`tests/test_sticker_history.py` covers newest-first history selection, current
message exclusion, CQ image parsing, OneBot image enrichment, and historical
source tracking.
`tests/test_sticker_reply.py` covers explicit reply-image loading, source
tracking, and the no-image result. `tests/test_image_reference.py` also covers
file-identifier recovery when a remote URL is unavailable.
`tests/test_sticker_agent.py` covers conservative defaults for incomplete local
function-tool calls, integer image-index normalization, and the one-search limit.
The release gate is pytest, Ruff, and strict mypy. `tests/test_sticker_caption_cache.py`
covers content fingerprints, provider/model isolation, and empty-result handling.
Container acceptance should send an image, then complete a meaningful group
conversation and confirm that the reaction agent searches once and sends no more
than one suitable saved image without an explicit tool name.

## Extension points

- Add GIF/video frame extraction and a verified native-library cleanup API.
- Replace keyword search with embeddings while preserving global access and
  source tracking.
